# intellisense — CLAUDE.md

## Purpose

Master intellisense governance system that all developers
inherit. **Changes here are not local** — they propagate to every developer
session via `~/.claude/` symlinks. Test thoroughly before shipping.

This repo is the source of truth for:
- **rules/** — baseline, language-specific, operational constraint files
- **skills/** — `/name`-invoked prompt templates (lazy-loaded; cost tokens only when invoked)
- **agents/** — sub-agent specs loaded on-demand
- **templates/** — per-stack CLAUDE.md + KB templates (Go, PHP, Angular, Node, Python, React, Flutter)
- **infrastructure/** — service-map.md (registry) and knowledge-base.md (term ownership)

Two modes share one tier model and one rule set:

- **Core mode** — the Go CLI (`cmd/intellisense`, `internal/`). Agent-neutral: policy in each repo's
  `.intellisense.yml`, rules vendored into `.intellisense/rules/`, instructions generated for Claude,
  Codex, Copilot and Cursor, gate in a pre-push hook and the GitHub Action (`action.yml`).
- **Live mode** — the Bash platform (`intellisense live install` or `setup.sh` → `~/.intellisense` + `~/.claude/`):
  prompt classifier, PreToolUse contract gate, skills, agents, optional telemetry/tracker/code graph. Its hooks ask
  the Go engine for every tier. Everything below the Go section is about this mode.

Stack: Go 1.22+ (CLI) and Bash (Live mode). Upstream: none. Downstream: every governed repository.

## Repository rules

- **No AI attribution** in commits or PR descriptions (no `Co-Authored-By` / "Generated with" lines).
- Branch from `develop`, PR into `develop`; `main` only receives `develop` via a `release: …` PR.
- PR titles are Conventional Commits; PR bodies keep the `## Docs update` block (`- Status:` / `- Notes:`).
- This repo runs its own gate: each Tier 1+ commit carries `Refs: #<issue>` and the change carries one
  `Change Contract:` line. Check with `go run ./cmd/intellisense classify` before committing.

## ⚠️ CRITICAL: Split-Path Architecture

**DO NOT move the `~/.intellisense/rules/` paths into `~/.claude/`.** This is intentional.

| Category | Path | Why |
|----------|------|-----|
| Baseline rules | `~/.claude/rules/baseline/` | Auto-loaded by Claude Code every session |
| Operational rules | `~/.intellisense/rules/operational/` | On-demand, `@`-referenced — not auto-loaded |
| Language-specific rules | `~/.intellisense/rules/language-specific/` | On-demand, per-repo stack — not auto-loaded |

Only `~/.claude/` auto-loads into every session, so keeping operational and language-specific rules out of it is
what makes lazy-loading work. Your organization's proprietary rules belong under `rules/organization/`.

## 3-Tier Architecture

```
Tier 1 (INTELLISENSE_SETUP — master)      ← this repo; edits affect next session immediately
    ↓ symlinks
Tier 2 (~/.claude/ — dev global)  ← generated by setup.sh, NOT symlinked; unique per dev
    ↓ repo-specific CLAUDE.md
Tier 3 (<service>/CLAUDE.md)      ← generated from templates, customized per service
```

**Stack inventory (single source — referenced below):** fill this in during
onboarding — list each repo your organization has run `setup-repos.sh`
against, grouped by stack (e.g. "3 Go: svc-a, svc-b, svc-c"). `setup-repos.sh`
runs per-repo; there is no default fleet baked into this framework.

## Critical Rules When Editing

**rules/baseline/** — affects every session, every repo, every task. Test
extensively; bump the version header. (e.g. security.md changes hit all developers.)

**rules/language-specific/** — affects all repos of that stack (see inventory above).
Test in ≥2 repos of the language; keep all 7 stack templates consistent.

**skills/** — lazy-loaded, so they cost tokens only when invoked. Lightweight
skills target <300 tokens; full workflow skills (`/code-review`, `/tdd`,
`/contract`, `*-test`) are necessarily larger — keep them as tight as the
workflow allows. Search existing skills before adding one; prefer a checklist +
`references/` pointer over prose; test end-to-end.

**agents/** — specs describe HOW an agent behaves, never business logic. Business
rules live in rule files; agents load them.
- Wrong: "code-architect should validate account balance before deduction"
- Right: that rule lives in a language-specific/operational file; the agent loads it

**infrastructure/service-map.md** — single source of truth for service
relationships. Adding a service updates all sections (service-map, knowledge-base,
templates, CLAUDE.md files). Test `/where-to-start` before shipping.

**infrastructure/knowledge-base.md** — term disambiguation for `/where-to-start`.
Multiple-writer terms → mark DISPUTED (forces a clarifying question). One line per
term; review OWNER fields quarterly.

**templates/** — copied (not symlinked) to each repo. Changing one → notify
affected stack owners; ask whether the change is universal or stack-specific; test
on a real repo first.

## Agents & Skills

Agents and skills are loaded on-demand; their own files are the source of truth.
This section is a pointer index, not a duplicate of their docs.

**Agents** (`agents/`):
- **strategic-architect** (Tier 1) — cross-service design, API contracts, deployment
  sequencing; auto-invoked when 2+ services mentioned
- **code-architect** (Tier 3, all repos) — single-service feature design
- Phase 4 code review is the `/code-review` skill

**Key skills** (full docs in each `skills/<name>/SKILL.md`):
- `/verify` — build → test → lint → security → financial; run before shipping any rule/skill
- `/learn` — extract session patterns, suggest memory updates
- `/plan` — analyze architectural decisions within INTELLISENSE_SETUP
- `/document-service --repo <path> --stack <stack>` — generate service docs
  (source-tree, project-context, api-contracts, architecture-overview + optional
  drift report). `--resume` continues an interrupted run; `--update-only` does a
  fast drift-check. Audits financial patterns (integer smallest-currency-unit,
  never float; SELECT FOR UPDATE; idempotency; your external billing system)
  and CLAUDE.md drift.

## Documentation Layers

This repo keeps its own design in `docs/L*` (checked by `bash bin/statutory-integrity.sh`): a requirement changes in
L2-001 first, a boundary or decision in L3-001 (add an ADR), setup or release steps in L4. Register every new layer doc
in its `-000-artifact-registry` in the same commit.

**Remediation (L6 → L6.1 → L7)** is for security reports and review batches — several findings handled as one
session: L6 audit + plan, L6.1 checklist + evidence, one row in `L7-001-master-registry`. An ordinary bug fix is an
issue, a PR and a CHANGELOG line.

## Domain Terms

- **intellisense** — this governance system: risk tiers, evidence gates and shared rules for coding agents
- **Skill** — `/name`-invoked in-context prompt template; `skills/<name>/SKILL.md`
- **Rule** — constraint file loaded into context; `rules/<category>/`

- **Hook Pack** — bundled pre-push hooks for a stack; installed from `hook-packs/`

## Run / Test / Build

```bash
# Whole suite (Go + Bash) and static checks — what CI runs
bash scripts/ci/test.sh          # optional-tool tests skip unless bd / code-review-graph are installed
bash scripts/ci/lint.sh
go test ./...                    # Go only

# Install / update platform
bash setup.sh                 # install ~/.claude symlinks from this repo
bash verify-setup.sh          # verify symlinks and required files

# Onboard a service repo (copies CLAUDE.md template, KB stubs, CI)
./setup-repos.sh --repo /path/to/repo --stack go|php|angular [--skip-claude-md] [--skip-ci]

# Service docs (inside a Claude session in the target repo)
/document-service --repo /path/to/repo --stack go   # full run
/document-service --resume                          # resume interrupted
/document-service --update-only                     # fast drift-check

# Tests / validation / restore
bash tests/test_setup.sh      # setup.sh installs correctly
bash tests/test_repos.sh      # per-repo onboarding
bash tests/test_restore.sh    # restore.sh cleanup
bash scripts/validate-intellisense-content.sh   # frontmatter, references, rules, agents
bash restore.sh               # undo installation, restore ~/.claude backups
```

**Knowledge Base load order:** files numbered 00–05 set Claude's load priority.
`00-system-context.md` is auto-loaded via the template's `@knowledge-base/00-system-context.md`
reference (kept <1.2k tokens); `01–05` are read on-demand. See
`templates/knowledge-base/README.stub.md` for the full file list and ownership.

**CI — refresh-docs.yml:** weekly doc refresh (Sun 20:30 UTC, cron `30 20 * * 0`):
detect stack → `/document-service --update-only` → commit if changed. Installed by
`setup-repos.sh` to each repo's `.github/workflows/`.

## Known Gotchas

- **Symlinks break if INTELLISENSE_SETUP moves** — path is stored in `~/.claude/config.json`.
  Re-run setup.sh in the new location (or edit config.json) to fix.
- **Keep rules compressed** — if a rule grows >5k tokens, split it
  (e.g. go-patterns.md → financial + standard). Skills are lazy-loaded, so prefer
  extracting detail into `references/` over a hard token cap. Bloated files slow every session.
- **Breaking baseline-rule changes need a rollout plan** — 7-day grace period,
  notify all developers, document in CHANGELOG.md.
- **service-map.md schema changes break `/where-to-start`** — test it with
  realistic requirements before changing columns/format.

## Session Completion

Full rule: [development-workflow.md → Approval Checkpoints](~/.intellisense/rules/operational/development-workflow.md).
Decomposed by reversibility — **local steps are mandatory; pushing needs approval.**

1. File issues for follow-up work
2. Run quality gates (tests/linters/builds) if code changed
3. Update issue status (close finished, update in-progress)
4. **Commit locally — MANDATORY**, never leave work uncommitted:
   ```bash
   git add <files>
   git commit -m "..."   # Tier 1+: a task trailer (Refs: #<issue>) on each commit, one Change Contract
   # sync your issue tracker if it needs a separate step (with Beads: `bd dolt push` — local-infra, always safe)
   ```
5. **Push only if approved this session** (`git pull --rebase && git push`). If not
   approved, stop and state in handoff: "committed locally on <branch>, not pushed
   — awaiting approval."
6. Clean up stashes / prune merged branches
7. Hand off: branch, commit, push status

**Never** push without this-session approval; **never** ask permission for the
local commit. If a pre-push hook blocks you, fix the genuine gap or surface it as a
possible false positive — do not bypass or game it (see reasoning-integrity.md
"gate-gaming").
